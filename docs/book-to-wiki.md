# 从一本书到一个 wiki：一步步的流程

以本仓库为例：把 Kunze《Technology Brewing and Malting》（960 页的扫描版 PDF）整理成中文酿造工艺 wiki。每一步写明做什么、产出什么、怎么检查，以及本项目的具体做法。

## 总览

| 步骤 | 做什么 | 产出 | 放在哪里 |
| --- | --- | --- | --- |
| 0 定目标与边界 | 读者、用途、范围、版权 | 一页说明 | README |
| 1 数字化 | 判断文字版或扫描版，OCR，页码映射 | 逐页文本、页码表 | 本地 `source-material/`，不进仓库 |
| 2 拆结构 | 目录 → 章节树 → wiki 的“原子单元” | 大纲 | 笔记 |
| 3 精读做笔记 | 按章读，记事实、机理、问题、页码 | 原始笔记 | 本地，不进仓库 |
| 4 设计数据结构 | 每个单元统一字段 | schema | `src/content/` |
| 5 改写成条目 | 自己的话、压缩、重组、统一术语 | 结构化内容 | `src/content/` |
| 6 核对 | 抽查数字、复算例题、标注示意 | 疑点表 | `src/wiki/coverage.js` |
| 7 生成页面 | 脚本生成 Markdown 和网页 | wiki 页面、交互网页 | `wiki/`、`site/` |
| 8 发布 | 选平台 | 可访问的 wiki | GitHub 等 |
| 9 维护 | 版本管理、补章节、改错 | 提交历史、issue | GitHub |
| 10 使用与复习 | 自测、复述、回到第 5–6 步改错 | 越用越准的 wiki | — |

## 0. 先定三件事

1. **读者和用途**：自己系统学习、查参数，还是给团队培训？用途决定 wiki 的最小单元。本项目是“学工艺、查参数”，所以最小单元是一个**工序**（如“糖化”“回旋沉淀”），而不是书的某一节。
2. **范围**：全书还是某几章。本项目第一轮先做了原书 p.32–731 的工艺章节，第二轮再补上引言、第 5 章的机械部分和第 7–11 章；覆盖情况记在[来源与覆盖范围](../wiki/sources.md)页。
3. **版权边界**：
   - 原书、扫描件、OCR 全文、贴近原文的逐页笔记，只放在本地，**不进仓库**（`.gitignore` 已挡住 `source-material/`、`*.pdf`、`ocr/`）。
   - wiki 里只放自己的话、事实性数据和页码引用，不复制段落、插图和表格。
   - 仓库默认私有；公开之前再检查一遍，并在 README 写明“学习笔记”的性质和原书信息。

## 1. 数字化与页码映射

1. **判断 PDF 类型**：`pdftotext book.pdf - | head` 有正文就是文字版；输出为空或乱码就是扫描版（本书是扫描版）。
2. **扫描版做 OCR**。可选工具：
   - macOS 自带的 Vision 框架（本项目用它，写一个几十行的 Swift 小程序；8 个进程并行，285 页只要一两分钟）；
   - Tesseract（开源、跨平台，中文和英文都有模型）；
   - ABBYY FineReader、Adobe Acrobat（商业软件，版面还原最好）。
3. **处理版面**：双栏排版要按栏重排文字；图注、页眉页脚、广告页要去掉或标出来。
4. **建立页码映射**：记下印刷页码与 PDF 页码的偏移（本书 PDF 页 = 印刷页 + 4）。插页和广告页会让偏移变化，每章开头核对一次。wiki 里一律引用**印刷页码**，这样拿纸质书也能对照。
5. **检查 OCR 质量**：数字、单位和符号最容易错（µm 识别成 um 或 mm、°C 丢失、公式错位）。关键数值回到原页图像核对。

## 2. 拆结构

1. 从目录抽出章节树（章 → 节 → 小节）和页码范围。
2. 决定页面粒度。常见三种：一章一页；一节一页；按主题重组。本项目按**工艺阶段**重组成 6 页（原料、制麦、麦汁、发酵、过滤稳定、灌装），每页包含若干工序；引言和第 7–11 章（成品啤酒、小型酿造、环境、能源、自动化）不属于工艺顺序，另设 5 个“专题”页。全书一共 68 个工序。
3. 找出“横切主题”，也就是分散在多章里的同一话题。本书的氧、热负荷、DMS、安全、损耗都分散在好几章，整理时要么合并成一个条目，要么互相链接。

## 3. 精读并做原始笔记（只给自己看）

- 按章阅读。每读完一节就记下：
  - **事实**：数值、单位、适用条件，以及页码；
  - **机理**：为什么是这个数；
  - **问题与对策**：书中讲到的故障和原因；
  - **例题和公式**。
- 原始笔记可以贴近原书结构，但**不直接发布**。
- 顺手记下疑点：书内前后矛盾、排印错误、OCR 可疑处。本项目就记下了 p.245 例题的算术错误、酯与充氧的两处相反说法等，见 `src/wiki/coverage.js`。

## 4. 设计数据结构（schema）

给每个单元定统一字段，并以数据形式保存，作为**唯一的事实源**：页面都从它生成，不要手改生成出来的页面。本项目每个工序的字段如下：

```js
{
  id: 's3-2',           // 稳定的编号，用作链接锚点
  no: '3.2', t: '糖化', en: 'Mashing', p: '214–247',  // 编号、标题、英文术语、原书页码
  goal: '…',            // 目的：一句话
  params: [['休止温度', '45–50 °C …'], …],           // 关键参数：名称-数值
  pts: ['…', …],        // 机理与要点
  faults: [['现象', '原因', '对策'], …],              // 常见问题
  w: ['chart:mash', 'tool:decoct'],                  // 关联的图和计算器
  q: [['问题', '答案'], …]                            // 自测题
}
```

数据格式用 JSON、YAML 或 JS 对象都可以。本项目用 JS 对象（`src/content/*.js`），因为交互网页可以直接读取它。

## 5. 把笔记改写成条目

- **用自己的话重写并压缩**：按读者需要重组，不要逐段翻译。本项目约 900 页的内容压缩成 68 个工序。
- **统一术语**：建立中英对照的术语表（`src/wiki/glossary.js`，119 条），全 wiki 用同一个译名。
- **统一单位和写法**：°C、hl、mg/L、×10⁶/mL、范围用“–”连接。
- **数字只留判断需要的**：范围、阈值、目标值，每个都能回溯到页码。
- **公式做成可复算的形式**：写成公式和示例，最好再做成计算器。本项目有 22 个，示例结果由脚本现场算出，不手抄。

## 6. 核对

1. 逐条抽查数值和页码，重点查 OCR 容易错的地方。
2. 复算书中例题。本项目用计算器复算：酒花例题得 3.57 kg α-酸，收率例题得 76.95%，用 Balling 公式从酒精和真正浸出物反推比尔森、小麦、出口型、博克、无醇啤酒的原麦汁，都与原书的平均值一致（误差 ≤0.01%）；p.245 的煮出醪例题和 p.796 的家酿酒花例题则因此发现了书中的算术错误。
3. 标明哪些是示意、哪些是推断。本项目的糖化和发酵温度曲线是依据文字描述画的示意图，已在页面上注明。
4. 有条件的话，请懂行的人审一遍，或用第二本资料交叉验证。

## 7. 生成页面

- **Markdown wiki**：`node scripts/build_wiki.mjs` 从数据生成首页、6 个阶段页、5 个专题页、公式页、程序与酶页、术语表、自测题、来源与覆盖范围页，共 17 页，并自动检查站内链接有没有断。
- **交互网页**：`node scripts/build_site.mjs` 把同一份数据拼成单文件网页 `site/index.html`（图表、计算器、搜索）。
- **交叉链接**：每个术语链接到它的工序；每个工序链接到相关的计算器和图表数据。

## 8. 选平台发布

| 方式 | 优点 | 限制 |
| --- | --- | --- |
| GitHub 仓库里的 Markdown（本项目默认） | 零配置、有版本历史、GitHub 上直接渲染表格和折叠答案 | 没有全文搜索和固定侧栏 |
| GitHub Wiki | 真正的 wiki 页面和侧栏 | 私有仓库需要付费计划；第一页必须先在网页上创建，才能用 git 推送 |
| MkDocs 或 Docusaurus 加 GitHub Pages | 有搜索、导航和主题，像正式文档站 | 需要构建；私有仓库开 Pages 需要付费计划 |
| Notion、飞书、语雀、Obsidian | 编辑方便，适合个人知识库 | 版本管理弱，批量生成和迁移不方便 |

本仓库现在的做法：仓库公开，Markdown wiki 直接在仓库里读；每次推送到 main，GitHub Actions 从 `src/` 重新生成交互网页、检查 wiki 链接，并发布到 GitHub Pages（<https://mrgreedcp-spec.github.io/kunze-brewing-wiki/>）；claude.ai 上另有同一页面。其他方式也准备好了：

```bash
# 1) 仓库内直接浏览：打开 wiki/README.md

# 2) GitHub Wiki：先在仓库的 Wiki 页签创建任意首页，然后
node scripts/build_wiki.mjs --gh-wiki build/gh-wiki
git clone https://github.com/<用户名>/kunze-brewing-wiki.wiki.git build/wiki-repo
cp build/gh-wiki/*.md build/wiki-repo/
cd build/wiki-repo && git add . && git commit -m "Update wiki" && git push

# 3) MkDocs 站点（本地预览）
pip install mkdocs
mkdocs serve        # 打开 http://127.0.0.1:8000
```

## 9. 版本管理与维护

- 改内容的顺序永远是：改 `src/` 里的数据 → 重新生成 → 检查 → 提交。提交说明写清改了哪一章。
- 用 GitHub issue 记录待补的章节和待核对的疑点。
- 补章节就是把第 1–7 步再走一遍，但只针对新的页码范围：本项目第二轮先对剩余的约 250 页做 OCR，按章写原始笔记，再新增 `src/content/07a…11-*.js` 数据文件（专题用 `topic:true` 标记，渲染时单独成组），补术语、覆盖范围和疑点表，最后重新生成、检查链接并重新发布网页。
- 公开前再检查一次：没有原文段落、扫描图和原书表格；README 写明来源，并建议读者购买原书。

## 10. 用起来

- 按工序读，读完做自测题；用费曼法把一个工序讲给别人听，讲不清楚的地方就是笔记的漏洞。
- 自测题可以导出到 Anki 做间隔复习（数据里的 `q` 字段就是问答对）。
- 复习时发现的错误和疑问，回到第 5–6 步修改数据，再重新生成。
